Phase 1: Schema and migration foundation

Context and outcome

Requirements and concrete schema

Use UUID primary keys, timestamptz, explicit non-null fields and named constraints. JSONB holds versioned payloads, not identities/FKs/current states. Store UTC instants; timezone scheduling belongs to #37. Preserve original display values separately from comparison keys.

Table group Required contract
accounts Immutable provider subject keyed by (provider, subject); owner association, active/disconnected state. One active Gmail account via partial unique index; inactive account history retained. No email-as-subject, access token, plaintext refresh token or automatic seed owner.
companies, contacts, company_contacts Stable company IDs; contact identity scoped to account and exact validated address comparison key. Company/contact membership unique per pair. Domains and names are indexed candidates, never globally unique company IDs. Shared domain must permit distinct companies.
company_identifiers, sources (company_id, kind, normalized_value) unique; provenance source reference/time and confirmation status. External source keys are scoped by account/provider/type. Only trusted stable external identifiers may receive a broader uniqueness constraint. Uncertain candidates remain unconfirmed; no auto-merge.
runs, run_steps Account, workflow kind, idempotency/input revision key, state, version, timestamps; (account_id, workflow_kind, logical_key, input_revision, execution_generation) unique; original generation is 0. Retry keeps logical input unchanged, links a terminal predecessor and increments generation. A unique predecessor link permits one successor; unique account-scoped retry submission key makes repeated retry requests idempotent. Cross-account/input predecessor links and nonconsecutive generations are rejected by FK/trigger. Concurrent retries return the same successor or a conflict, never two runs. Steps unique by (run_id, step_key, input_revision), with persisted input/output references and state. No worker or scheduling loop.
revisions, artifacts Immutable typed document/action content revisions; unique (record_id, revision); content hash is validated/indexed, never unique globally or per record. Equal content across records and A/B/A revision history are valid; submission keys handle duplicate requests. Artifact metadata includes storage key, checksum, byte length, MIME, role, retention class, source revision and deletion marker. Bytes remain in private root; no public absolute path.
actions, action_revisions Stable logical action key scoped by account and kind; current revision and blueprint action state. Immutable revision binds kind, canonical payload, exact ordered destination representation and attachment IDs/hashes. Cross-account/revision links must be rejected by composite FKs or equivalent database constraints.
approvals, action_attempts Append-only approval/rejection history, actor reference and immutable action revision; one effective decision per revision (submission idempotency). Attempts unique by (action_id, attempt_number), recording claim token/fence, start/finish, result, nullable provider ID and sanitized failure code.

Create audit history for state changes with IDs, revisions, prior/new state and decision metadata only. Domain services in phase 2 enforce valid relations, while DB constraints prevent invalid references and contradictory current records even under concurrent writers. Keep human-readable content out of operational logs.

Do not add budget, scheduler cursor, profile settings or OAuth encryption implementation for unrelated issues. Future migrations add those concrete records when their owning work is selected. An encrypted-token field is not useful until #15 supplies encryption/key handling; do not create a plaintext placeholder.

Phase 2 · Transactional state

Phase 2: Transactional workflow state

Context and outcome

Depends on phase 1. Read blueprint state contract, phase 1, and issues #19, #20. Deliver a persistence-level state machine with concurrency guards. Authenticated approval handlers and provider action execution remain downstream.

Requirements and transition policy

Statuses must use exactly the blueprint vocabulary. State CHECK constraints alone cannot validate old-to-new edges. Use a database transition trigger/function plus state-version compare-and-swap in persistence operations. Enforce append-only revision/approval history against ordinary app operations. Document the privileged migration-role boundary; no claim of protection from a database administrator.

Validated run transitions:

From Allowed next
queued running, canceled
running awaiting_owner, succeeded, partial, failed, canceled
awaiting_owner queued, canceled
succeeded, partial, failed, canceled none; an explicit retry creates a new run linked to its predecessor

Restart keeps a running record and resumes eligible unfinished steps by persisted input revision. It does not replay completed steps, mutate terminal states or start a worker in this issue. Storage only provides pending-work queries and durable checkpoints.

Action from Allowed next Guard
draft awaiting_approval Complete immutable revision exists
awaiting_approval approved, draft Approved requires matching current owner decision; rejection returns draft
approved claimed, draft Claim rechecks exact revision approval transactionally; edit returns draft on new revision
claimed succeeded, failed_known, unknown Current claim token/fence; no provider replay
failed_known approved, draft Return to approved only for explicit safe-retry evidence and still-valid exact-revision approval; otherwise new revision returns draft. #20 owns proving retry eligibility
unknown succeeded, failed_known Explicit reconciliation/resolution evidence; never auto-claim or auto-retry
succeeded none Immutable terminal outcome

A new action revision creates a new immutable row and invalidates old executable authorization without deleting approval history. Editing a claimed or unknown revision is refused; retain uncertain intent for #20 to reconcile. Succeeded actions stay unchanged; a distinct new logical action requires distinct intent. Approval, current revision, kind, exact destinations and attachment hashes must agree at claim. Different action kinds cannot share approval.

A failed_known action may reuse still-valid approval only for the identical immutable revision after #20 establishes no external effect; this transition never applies to unknown. Persist retry evidence and repeat all claim validity checks.

Claim/attempt creation uses a short transaction and monotonic fence/version. Unique live-claim constraint and row locking/CAS make two simultaneous attempts produce one winner. Store lease and heartbeat fields but do not implement a worker timer. Expiry of an external claimed action permits only recording unknown; it never grants retry. Do not represent safe read/research leases as external send actions.

Phase 3 · Projection & artifacts

Phase 3: Canonical projection and artifact storage

Context and outcome

Depends on phase 2. Read graph/vector contract, phase 1, phase 2. Deliver durable canonical relationship facts, outbox/checkpoint storage and private artifact I/O. The skeleton has no existing worker despite blueprint language; do not invent one here.

Requirements and schema additions

  • Canonical relationship rows reference company/contact/meeting/report/source identities through stable typed record/revision references, with evidence and confirmation status. Add only minimal source/meeting/report identity metadata needed by these references; no ingestion or report generation.
  • Mutation + outbox event commit together. Each event has stable ID, entity ID/type, revision, operation (upsert/delete), schema version, timestamp and canonical reference; do not duplicate private document bodies in event payloads.
  • Outbox uniqueness (entity_type, entity_id, revision, operation) prevents duplicate logical events. One event can target both stores; store separate delivery rows keyed (event_id, target) and target checkpoint/version metadata. One store's success cannot mark another successful. SQL storage permits pending, applied and retry metadata without a running projector.
  • Store tombstones and monotonically checked entity revisions so delayed updates cannot resurrect deleted content. Preserve enough canonical provenance to rebuild graph without new model inference. Use per-entity revision safety; a single global high-water mark must not skip out-of-order unprocessed events.
  • Embedding metadata links chunk/source revision, provider/model/version, dimension, vector artifact hash/key and index-generation identity. Dimension positive; generation/model/dimension must match on reference. Generated vectors belong to private backed-up files. No model/provider default, embedding request or Qdrant collection creation in this issue.
  • Artifact classes distinguish retained approved reports from 30-day temporary downloads/intermediates. Store retention metadata only; #25 owns cleanup/deletion execution. Persist deletion markers without cascading away immutable action/approval history.

Architecture and artifact boundary

Store artifact bytes under a configured private root with generated opaque relative keys. Validate root ownership/permissions, reject absolute/traversal/symlink escapes and non-regular files. Never accept arbitrary client paths. Atomic exclusive writes, checksum verification and an explicit pending/ready state handle the DB/filesystem transaction gap. Publish ready metadata only after durable file write; on rollback/crash, unreferenced files remain identifiable for guarded cleanup. No broad automatic deletion.

Duplicate content hashes need not imply one shared physical file: preserve per-artifact retention/deletion ownership. This avoids premature shared-reference garbage collection. Use stdlib file, hashing and path utilities; no object-store abstraction. Parameterized SQL and versioned payload validation remain mandatory.

Phase 4: Recovery and delivery evidence

Context and outcome

Local operational contract

Finish the guarded local helper introduced in phase 1 as scripts/storage-snapshot.py, with documented subcommands backup, migrate and restore. Exact CLI flags are implementation contracts, not current runnable commands. Private config supplies source/target connection and artifact root. Never put credentials in command arguments or public error output.

  • backup: refuse unsafe/shared/symlink staging, require app writers quiesced, use pg_dump custom format against PostgreSQL 17 with compatible client and copy matching private artifact bytes. Output protected manifest with DB/Alembic revision, hashes and counts; verify dump readable. Use restrictive directory/file modes. Failure must not create a success manifest.
  • migrate: the only documented local upgrade route; take a fresh verified backup before Alembic changes, then apply one head while retaining the same maintenance exclusion from before backup through upgrade completion or abort; never release it between subprocesses. No automatic API startup migration. Refuse active application writers, incompatible DB revision and incomplete snapshot. Fresh disposable empty databases still get backed up first.
  • restore: validate snapshot manifest and every required file/hash; refuse live/nonempty destination and path overlaps with source or snapshot. Restore to explicitly isolated owned target with sending/scheduling absent or disabled. Never overwrite source. Verify schema revision, constraints, counts, approval/action revisions and artifact references/hashes. Return nonzero for corrupt/incomplete restore; do not claim success after only pg_restore.

Because #12 introduces no application data endpoints or worker, local migration requires stopping other DB writers. Use an explicit maintenance protocol and DB-level exclusion/advisory lock shared by all persistence writes; do not rely solely on an unchecked human assertion of quiescence. All application DB/artifact write operations acquire the shared maintenance lock before writing. A parent connection holds the exclusive maintenance lock through matching DB/file snapshot and, for migrate, through Alembic success or failure handling. Do not release it in the backup-to-upgrade interval or when spawning pg_dump/Alembic. A concurrent write must fail or wait boundedly without creating a mixed snapshot. Future workers must follow this protocol. Secrets use private file/environment and sanitized errors; never shell-source configuration.

The helper covers local migration safety only. Reserve scripts/backup.sh and scripts/restore.sh for the accepted production restic/R2 interfaces owned by #42. No token decryption/access checks can pass before #13/#15; no actual projection rebuild can pass before projector/retrieval work. Mark those downstream checks pending explicitly.
